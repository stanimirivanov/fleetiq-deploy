# Offline Kubernetes demo supporting-service feasibility

## TL;DR

Keep the existing RustFS digest as the first standalone persistent-store qualification candidate. Prepare static Sofia raster maps from permitted OSM source downloads; do not scrape public tiles. Isolate Chromium at OS-user/home/trust-database level, because a separate profile alone is insufficient. These are evidence-backed planning selections, not live qualification or proof the complete stack fits.

Research for [supporting-service feasibility](https://github.com/stanimirivanov/fleetiq-deploy/issues/93) and [the supporting-service decision](https://github.com/stanimirivanov/fleetiq-deploy/issues/86), checked 2026-11-22. This throwaway research branch is not intended to merge.

### Inferred deployment design and qualification gate

Use a single private S3 service and one persistent data volume, with explicit storage capacity/retention, HTTPS, a disabled or separately restricted console, and application credentials limited to the archive namespace. Provision the bucket/policy administratively; do not give runtime archive clients bootstrap credentials. Package the pinned image and required bootstrap tooling for offline installation. This is deployment design work for the owning deployment repository; the platform owns any missing runtime configuration or client trust support.

Before accepting the candidate, qualify the **exact image digest** with the platform client: create an absent key; retry identical content; reject different content at an existing key without changing bytes; race distinct payloads for the same absent key and prove exactly one winner; verify authenticated reads and restart/pod-replacement persistence; verify correct and incorrect certificate/CA/hostname cases; prove intended IAM allow/deny behavior; and exercise offline cold start, bounded storage exhaustion, restart/recovery and representative archive load while recording CPU, memory and disk use. Existing identical-content concurrency tests alone do not prove single-winner semantics for competing payloads. Preserve the existing adapter's integrity verification.

No Kubernetes, provider, TLS, IAM, persistence, performance or offline tests were run in this research. Rolling upstream docs and upstream issue closure are supporting evidence, not version-specific acceptance evidence; fetching the 1.0.4 conditional-write source path through web retrieval failed, so no claim is made that its source was inspected.

## Offline Sofia map and Chromium trust research

Research date: 2026-11-22. This is source-based feasibility research, not a generated map, resource benchmark, or tested browser setup.

## Recommendation

Prepare an immutable, bounded Sofia raster XYZ tile pack from lawfully downloaded OSM source data. Serve it as static same-origin assets during the demo. Perform extraction, vector generation and raster rendering before offline runtime. Keep Chromium in an isolated browser container or dedicated OS user with its own home/trust database; a browser profile alone is not sufficient evidence of CA isolation.

## Source acquisition and redistribution

Do not prefetch either OSM public raster or vector tile endpoints: both official policies prohibit bulk/offline archive creation. Their availability does not grant permission to scrape. [OSMF raster policy](https://operations.osmfoundation.org/policies/tiles/), [OSMF vector policy](https://operations.osmfoundation.org/policies/vector/).

A concrete permissible input is Geofabrik’s Bulgaria `.osm.pbf` extract. The provider offers downloads specifically for reuse and states that all OSM-derived downloads are ODbL 1.0, with attribution and retention of the licence for derived databases. Select an explicitly dated extract during preparation; record URL, timestamp and SHA-256, rather than relying on mutable `latest`. [Bulgaria downloads](https://download.geofabrik.de/europe/bulgaria/index.html), [Geofabrik reuse terms](https://www.geofabrik.de/en/data/download.html).

Publicly distributed derived databases must satisfy ODbL; generated raster imagery is a Produced Work, but creating it from a derivative database can still trigger the derivative-database access obligation. A conservative package includes the exact bounded source/derived database used, transformation recipe, source provenance and ODbL licence text alongside the tile pack. Do not assert that rasterization removes the source-offer obligation. See sections 4.2–4.6. [ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/).

Show visible, legible “© OpenStreetMap contributors” beside the map and expose origin/licence information. The usual copyright link is permitted, but offline operation should also offer a local attribution/licence page with the canonical origin URL as text. Attribution need not cause an automatic outbound request. Preserve separate notices for any style, font and sprite assets. [OSMF attribution guidelines](https://osmfoundation.org/wiki/Licence/Attribution_Guidelines).

## Concrete preparation and packaging route

1. Download and hash the selected Bulgaria source during online preparation. Extract a buffered Sofia polygon or bounding box with Osmium, preserving complete ways/relations as required by the chosen extraction strategy. The exact buffer must be validated at map edges. [Osmium manual](https://osmcode.org/osmium-tool/manual.html).
2. Generate local vector tiles from that extract using pinned tilemaker plus pinned JSON configuration/Lua processing. It supports standalone MVT files, MBTiles and PMTiles without a database; its documented OpenMapTiles-compatible recipe is a practical starting point. Generation memory is separate from runtime; use a bounded extract and optionally on-disk store. [tilemaker](https://github.com/systemed/tilemaker), [running tilemaker](https://github.com/systemed/tilemaker/blob/master/docs/RUNNING.md).
3. Use a reviewed local style and fully local fonts/sprites in a pinned preparation-only TileServer GL renderer. Its full version renders PNG/JPEG/WebP XYZ endpoints; `tileserver-gl-light` cannot render raster. Configure local MBTiles, style, font and sprite paths; audit all style references and any auxiliary landcover/coastline datasets. Avoid copying a sample remote style unchanged. [TileServer GL endpoints](https://tileserver.readthedocs.io/en/latest/endpoints.html), [configuration](https://tileserver.readthedocs.io/en/latest/config.html).
4. Enumerate the finite XYZ set for chosen bounds and zoom levels, fetch only from this self-hosted renderer, and package output files, manifest/checksums, attribution and source offer. Stop/remove the renderer before demo runtime. A FleetIQ-owned minimal style (roads, parks, water, labels) avoids inherited style/sprite complexity; alternatively review the complete OSM Bright licence and every included asset. Noto font licences are available upstream, but verify the exact selected font’s redistribution terms and Cyrillic coverage rather than assuming all glyphs are present. [OSM Bright licence](https://github.com/openmaptiles/osm-bright-gl-style/blob/master/LICENSE.md), [Noto licence](https://github.com/notofonts/noto-fonts/blob/main/LICENSE).
5. Serve static tiles through the existing local edge. The runtime MapLibre raster style needs no glyph/sprite URLs because labels are already pixels. Set source `bounds`, `minzoom`, `maxzoom`, `tileSize`, XYZ scheme and attribution. MapLibre documents these fields and overzoom behavior; source bounds alone are not a camera constraint, so constrain or clearly define supported camera navigation in the UI where necessary. [MapLibre source specification](https://maplibre.org/maplibre-style-spec/sources/).

This architecture removes rendering/database work from the running map service. It does not establish measured CPU, RAM or storage consumption. Keep map build tooling outside the steady-state 4 CPU/12 GiB node budget; measure the actual full demo including ingress, storage cache and browser placement. A static vector pack is a legitimate alternative: tilemaker produces it directly, but runtime then needs local glyph/sprite assets and client vector rendering. Raster has the smaller change surface given the current synthetic raster fixture.

## Qualification gates, not invented sizing

Determine the bounding polygon from all seeded routes and viewport padding; define supported minimum/maximum zoom and whether overzoom is accepted. Record complete tile count, encoded size, uncompressed disk size, first-load requests, runtime CPU/RAM and render latency. No area, zoom ceiling or MiB claim is qualified by this research.

Require visual evidence of recognizable Sofia road structure, readable Bulgarian/Cyrillic labels, useful route context, light/dark behavior and clean boundary handling. Traverse every supported zoom and representative corners. Validate missing/corrupt tile handling, no external fallback and a fresh-cache cold start with external egress denied. Browser request evidence must cover styles, TileJSON, tiles, fonts, sprites and application assets. Labels without network access are a specific acceptance check.

## Linux Chromium CA isolation

Chromium’s Linux certificate documentation explicitly uses an NSS **shared** database under the OS user’s home. Current docs say Chromium M146 defaults to `$HOME/.local/share/pki/nssdb`, while an existing `$HOME/.pki/nssdb` takes precedence. Consequently `--user-data-dir`/a dedicated Chrome profile does not by itself isolate an NSS CA import from other browsers using that same OS-user database. [Chromium Linux cert management](https://chromium.googlesource.com/chromium/src/+/main/docs/linux/cert_management.md).

Recommended implementation: a dedicated browser container with a dedicated non-root user/home and owned profile volume, or a dedicated OS user with its own home. Do not mount the host user’s NSS or system trust stores writable. Import only the demo CA certificate into that isolated user’s actual NSS DB using the documented `certutil` server-CA trust flags `C,,`; keep the CA private key outside the browser. Pin and test the exact Chromium build because distro packaging/version affects paths. This container/user isolation is an engineering inference from the documented shared home database, not a claim that Chromium offers a profile-local CA switch.

Acceptance: normal navigation succeeds with valid SAN, hostname and chain; an equivalent fresh browser trust DB without the CA rejects the endpoint; a deliberately mismatched hostname or untrusted test chain still fails. The host user’s NSS and system stores remain unchanged, and cleanup removes the owned browser state. No `ignoreHTTPSErrors`, `--ignore-certificate-errors`, interstitial bypass or equivalent TLS bypass is admissible. Verify the pinned browser in the actual GUI/automation mode intended for the demo; research has not executed that test.
